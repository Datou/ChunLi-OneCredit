## 结论

- **Python 锁步评测**读数是 README 里 88/100 的来源：肯在 100 次自然赛程里 99 次打到、97 次过关，5% 抖动下独立开局 7/8。
- **网页**用同一份权重、同一份 ROM、同样的 5% 抖动，肯单场只有 **10–12/20（50–60%）**；四轮第 8 关复测（10/20、11/20、12/20、12/20）合并 **45/80（56%）**。Python 自然赛程里肯是 93/97（95.9%），两者 Fisher 精确检验 p≈1e-10；用同口径的自然推进比较（网页 8/12）p≈0.005。
- 差距不是全局的：另外 11 关网页合计 193/220（87.7%），Python 85/88（96.6%）。肯是唯一一关稳定掉到 50–60% 的。
- 把观测管线逐位对齐训练代码（掩码 0 像素差、观测最大 1/255）只把肯从 11/20 提到 12/20；权重哈希、推理路径、存档文件内容都已排除。
- 目前最可信的原因：**同一个存档在 1.7.5（训练）与 1.7.6（网页）里跑出来的对局会分叉**。载入同一份状态、各跑一帧后工作 RAM 就差 41 字节；用完全相同的 240 帧输入脚本推进，到第 240 帧双方血量已经不同（109 vs 139）。肯的平均对局最长（4055 帧），分叉代价最大。
- 因此**网页读数不能直接对照 README 数字**。要么换回 1.7.5 的 core，要么承认网页是"近似同策略"，并在界面上标注口径差异。

## 2. 复测方法

- 网页单场复测每局重新读档，避免把上一场的残留算进来；另有一轮"从自然对局打进肯"的复测，专门和 Python 的自然赛程对照。
- 网页判胜直接读 RAM：`p2KO` 增加 2 为胜、`p1KO` 增加 2 为负，与 Python 的 `evaluate.fixture` 判胜口径相同。
- 抖动注入方式一致：每个物理帧 5% 概率把该帧输入延后 1–5 帧，队列不允许后来的输入超车。
- 网页复测走无头 Chrome + CDP（本地脚本 `_web_verify/cdp_probe.mjs`，未入库），页面加载完成后直接调用 `session.loadFixture()` 与 `session.stepFrame()`，不经过实时渲染循环，因此结果可复现。
- 权重核对：网页 `web/models/chunppo_p27.json` 内记录的 checkpoint SHA-256 与发布权重一致；SIMD dense 与纯 JS dense 的最大 logit 差 3.8e-6，argmax 相同。

### 3.1 观测管线

训练用的 `chunppo/env.py` 观测是：RGB → 灰度（`cv2.COLOR_RGB2GRAY`，四舍五入）→ 前景差分 + Otsu → `GaussianBlur(5×5, sigma=0)` → 膨胀 → 双线性缩放到 84×84。网页最初的移植有三处"看起来等价、实际不等价"：

1. 灰度用浮点 `0.299/0.587/0.114` 后直接截断，训练用 cv2 的四舍五入；截断让每个像素系统性偏低，前景差分的掩码边界随之改变。
2. `cv2.GaussianBlur(ksize=5, sigma=0)` 用的是 `getGaussianKernel` 的小核表，即每轴 `[1,4,6,4,1]/16`，不是 σ=1.1 的高斯采样。这一条对掩码边缘影响最大。
3. `cv2.resize(..., INTER_LINEAR)` 的系数是 11 位定点、两遍 22 位后再舍入；浮点实现每次都会差 1 个灰阶。边界处理也统一成 cv2 的 reflect-101。

改完后与 Python 逐帧对照：掩码 0 像素差，84×84 观测最大差 1/255，40 个采样状态里 argmax 仍有 1 个翻转。观测已经不是主要误差源，但肯只从 11/20 变成 12/20。改动落在 [web/observer.js](../web/observer.js)（提交 `84a35be`、`5eff1e2`、`f741559`）。

### 3.2 对齐敏感性

把整帧画面（320 宽）水平平移几个像素后再走同一条观测管线，肯掉到 3/20。这说明"对齐"这件事本身极敏感，也说明当前的裁剪位置不是偏了才导致 12/20——任意偏移只会更差。

### 3.3 存档重建

随网页发布的第 8 关存档，与训练用的 `Stage08.Ken.state` 在 64 KiB 工作 RAM 上有 11,708 字节不同（约 18%）。用转换脚本从训练状态重新生成一份存档后：

- 文件里的工作 RAM 与训练端读档后的内容逐字节一致（0 字节差）；
- 用这份存档复测，肯仍是 12/20。

所以问题不在存档文件本身：把它换成与训练端逐字节一致的版本，胜率没有变化。

### 3.4 原生 1.7.6 开局

反过来试：不用训练状态，在网页里从上一关的开局存档打进去，打到目标对手的可控开局时序列化，作为该关存档。抓到第 2、3、5、6、8、9、11、12 关；第 4 关（隆）因为敌方 ID 为 0、与"没有敌人"重合而无法判定；第 7、10 关各试了 6 次，都卡在前一场（第 7 关 6 次全停在布兰卡），没拿到可控开局。

结果与预期相反：用原生抓的第 8 关开局，肯只有 **5/20**，比转换存档的 12/20 更差。说明"原生"不等于"训练时的开局条件"——相机相位、RNG、双方距离都可能不同，而策略对这些很敏感。

### 3.5 开场时机

一次改变"把控制权交给策略的时刻"的变体（`ken-walk`）没有改善，落在 10/20。这一项没有继续深挖，因为 3.4 已经说明开局状态的影响可以比观测管线大一个量级。

### 3.6 权重与推理

- 权重文件记录的 checkpoint 哈希与发布权重一致。
- SIMD dense 与纯 JS dense 的最大 logit 差 3.8e-6，argmax 相同；关掉 SIMD 后第 1 关仍是 20/20。
- 因此不是"网页跑的不是同一个网络"。

## 4. 关键实验：同一存档、同一输入，两个 core 走散

这一节是整轮排查里唯一能把问题指向 core（或它恢复旧存档的路径）的证据。

用重建后的第 8 关存档（工作 RAM 与训练端一致），两侧都从读档后开始，执行同一段 240 帧输入脚本（60 帧中立、60 帧右、60 帧右下、60 帧右上），在 0/60/120/180/240 帧各转储 64 KiB 工作 RAM：

| 帧 | 工作 RAM 差异字节 | Python 春丽 HP | 网页春丽 HP |
| ---: | ---: | ---: | ---: |
| 0 | 41 | 176 | 176 |
| 60 | 50 | 176 | 176 |
| 120 | 22 | 176 | 176 |
| 180 | 763 | 139 | 139 |
| 240 | 908 | **109** | **139** |

第 0 帧那 41 字节的分布：

- 16 字节在 `0x80xx` 游戏全局区，含 `0x8002`、`0x8005`、`0x801a`、`0x80b2` 等回合/模式字段；
- `0x973e` 1 字节；
- `0xa278`、`0xa27a` 2 字节；
- `0xfbc2–0xfbf1` 的 22 字节落在 68k 栈上。

两个 core 的状态缓冲区都是 1,036,288 字节，工作 RAM、显存、VDP 寄存器同偏移，但控制字段和 CPU 上下文的后续布局不同（见 [网页存档兼容性](state-format-compat.md)）。合理推测是 1.7.6 在恢复 1.7.5 的状态后，某些内部字段（CPU 周期计数、栈内容、新的 VDP/定时器状态）拿到了不同的值，于是**第一帧执行就不一样**；差异随后被游戏逻辑放大，到第 240 帧已经打出不同的伤害。

这也解释了为什么 Python 侧 8 局能赢 7 局、网页侧 20 局只赢 12 局：策略本身没有变，变的是它在网页里"实际经历的对局"。

## 5. 为什么偏偏是肯

- **对局最长。** 第 8 关 20 局平均 4055 帧、最长 5292 帧，是 12 关里最长的（第 7 关古烈 4042 帧次之）。分叉随帧数累积，长对局最吃亏。
- **容错最低。** 从对局看，肯的 AI 会贴身抢攻、用升龙对空，策略需要精确的距离和时机；一次分叉就可能让整局节奏反转。古烈虽然也长，但对局结构更宽容（17/20）。
- **不是"打满 8 场累了"。** 单场独立读档同样只有 10–12/20，所以不是连续赛程的状态累积。
- **不是抖动。** 5% 抖动下 Python 仍有 7/8；网页用同样的抖动注入。

## 6. 排除项与未成立的解释

- **观测管线**：已对齐到 0 像素掩码差、1/255 观测差，肯没有明显改善 → 排除。
- **权重/推理**：哈希一致、SIMD 与纯 JS 一致 → 排除。
- **存档文件**：重建后与训练端 0 字节差，仍然 12/20 → 文件内容不是原因（运行时恢复后的差异另算）。
- **网页调度（4 帧一决策、实时性）**：复测直接调用 `stepFrame()` 同步推进，不经过实时循环，结果一样 → 不是掉帧造成的。
- **肯的开局位置特殊**：原生抓的开局更差（5/20），说明开局条件确实重要，但它不是"换个开局就回到 97/99"的开关。

## 7. 下一步

1. **用 1.7.5 源码编一版 WASM**（`scripts/build_gx_wasm.ps1` 已有），在同一套复测里跑第 8 关。如果肯回到 17–18/20，core 版本就是定论；这是最直接、也最可能一次解决问题的验证。
2. **如果必须留在 1.7.6**：对比两版的状态恢复路径（`state.c`、CPU/VDP 上下文），找出新增或语义变化的字段，在转换时补齐；目标是让第 0 帧的 41 字节差异归零，再看分叉是否还扩散。
3. **开局策展**：在 1.7.6 里为每关采 5–10 个原生候选开局（不同 RNG/相机相位），先粗筛，再按 20 局/关复测，选与训练条件最接近的一个。至少能把"开局条件"这个变量钉死。
4. **统计口径**：20 局/关的 95% 区间约 ±15–22 个百分点，要支撑 README 级别的结论需要 50–100 局/关；复测脚本应固化下来，避免每次手搓。
5. **产品层面**：如果最终不换 core，网页上应标注"浏览器实时读数与 README 的 Python 锁步评测存在差异"，避免读者把两者直接对比。
